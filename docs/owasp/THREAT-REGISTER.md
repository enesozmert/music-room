# Threat Register

Subject V.6 requires more than protections: *"you must identify other dangers and describe the
protection measures that can be implemented"*. This is that document.

**A written accepted risk is an engineering decision. An unwritten one is an oversight.**
Evaluators ask what you did *not* protect against; this table is the answer.

## Status

**Design-stage register.** 29 threats. Slice S0 landed the first verified rows, S1 added T-25,
T-26 and T-27, and closed T-25; S5 closed T-06 — the reorder race subject V.2.3 grades — and gave
T-11 its first evidence. Every other mitigation below is *designed*, not verified.
The Verified column stays empty until a test, a config artifact or a named code path proves it.

## Legend

Likelihood and Impact: L / M / H. Residual = what remains **after** the planned mitigation.

| T-26 | Development-only `LoggingMailService` writes the email verification link **and the password reset token** to the application log | M | M | registered as `IMailService` only when the host environment is Development; `AddInfrastructureServices` throws `InvalidOperationException` at start-up in any other environment rather than falling back silently or booting with no sender. | T-27 | No security event is logged when a credential endpoint refuses a request: a failed login, a rejected refresh token and a detected refresh-token **reuse** all leave no record beyond the Serilog request line | M | M | the A09 event list in [[owasp-top10-checklist]]: log failed login, lockout, token reuse, authorisation denial and rate-limit trip, through the audit behaviour of slice S2 ([[ADR-0019-hub-action-auditing]], SDD §13.4) | **closed 2026-09-28 by SPEC-009.** Every credential refusal now leaves an `audit_records` row that says which refusal it was: `refused` for a wrong password or an unknown token, `throttled` when the account is out of attempts, `expired` for a spent window, and `reusedetected` when an already-rotated refresh token revoked a family — that last one naming the account whose family died. | T-28 | Neither a password reset nor a logout revokes access tokens already issued: a JWT minted before either stays valid until `exp`, so a thief who signed in moments earlier keeps API access for the remainder of that window | M | M | the 15-minute access-token lifetime (SDD §13.1), which is why the lifetime is short; a `jti` or per-user not-valid-before denylist checked on every authenticated request would close it entirely | **accepted.** Revoking refresh families ends every session's ability to continue, which is the control the contract promises; the remaining exposure is bounded by the token lifetime and cannot exceed **15 minutes and 30 seconds** — 15 minutes signed plus the 30 seconds of clock skew the bearer handler allows (owner decision, 2026-09-28; the handler's five-minute default would have made it 20 minutes). SPEC-010 widened this row from reset to logout as well, for the same reason: a stateless token cannot be recalled without state on every request. A denylist needs storage and the bearer middleware that does not exist yet, and it makes every authenticated request read that state — a cost paid on every request to shorten a 15-minute window. Revisit if the access-token lifetime is ever raised | owner, 2026-09-27, on SPEC-007 | S1: `Reset_WithTheIssuedToken_RevokesEveryRefreshTokenFamilyAsync` proves what a reset **does** revoke; S2: `Logout_ThenRotatingTheEndedSession_Returns401Async` proves the same for logout, and `BearerValidationTests.Sessions_WithAnExpiredToken_Returns401Async` proves the window closes. The window itself is stated, not measured |
| T-29 | The audit log is fail closed: a command whose `audit_records` insert fails is rolled back and answers `500`, so a fault confined to the audit table stops every mutating endpoint | L | H | the record and the effect share one transaction, so neither can exist without the other (SDD §13.4, §10.7); the table has two indexes and no foreign key, so the write is as cheap as an insert gets | **accepted, deliberately.** The alternative was fail open, which allows an action nobody can account for — the exact gap subject V.6 asks about. The owner chose evidence over availability on 2026-09-27, knowing an audit-table fault becomes a total mutation outage and that a defence demo would die on it. Reads, health probes and the OpenAPI document are unaffected, so the service stays diagnosable while refusing to act unrecorded. **SPEC-009 widened what this covers:** a refused attempt now writes a row too, so a guessing run writes one row per attempt — bounded by the limits in SDD §13.3, 5 per account per 5 minutes and 20 per IP per 5 minutes, which is the volume the owner accepted on 2026-09-28 | owner, 2026-09-27, on SPEC-008 | S2: `AuditBehaviourTests.Handle_WhenTheSinkThrows_RollsBackAndRethrowsAsync` proves the rollback and the rethrow |

## Explicitly out of scope

| Not defended against | Why |
|---|---|
| A determined attacker with unlimited resources | subject V.6: *"your API is not expected to be unbreakable"* |
| Physical device compromise | the token is in the platform secure store; a rooted device is outside our control |
| Supabase platform compromise | vendor trust boundary, stated rather than pretended away |
| Sybil accounts (T-05) | email verification raises cost; full prevention needs identity proofing this project will not build |

## Maintenance

- A finding from [[owasp-top10-checklist]] or [[owasp-api-top10-checklist]] that is not fixed in
  the pull request gets a row here **before** that PR merges.
- Fill Accepted by with a real name when the team agrees to carry a residual risk.
- Fill Verified with the test or artifact that proves the mitigation, once it exists.
- Never delete a row. Close it by pointing at the evidence.
